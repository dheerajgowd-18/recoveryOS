# RecoveryOS Modeling & Operational Assumptions

This document explicitly details all foundational assumptions, modeling abstractions, and operational boundaries governing RecoveryOS.

---

## 1. Environment & Simulation Assumptions

### 1.1 Synthetic Environment Nature
- **Assumption**: All scenario evaluations, customer archetypes, and payment transitions evaluated in the benchmark suite are generated by the synthetic simulation environment (`simulator/`).
- **Implication**: While error codes and failure behaviors mirror production Razorpay diagnostics, synthetic simulations evaluate algorithmic behavior and safety mechanics rather than proving empirical production causal uplift on live merchants.

### 1.2 Observable Recovery Context & Sequestered Potential Outcomes
- **Assumption**: The agent and policy receive only `ObservableRecoveryContext`, strictly sequestering latent archetypes, ground-truth failure classes, and potential outcomes $Y(a)$.
- **Implication**: The system must infer or receive a structured diagnosis from observable error codes, descriptions, reasons, and historical metadata. Potential outcomes are used solely by `EvaluationHarness` for evaluator-side scoring.

### 1.3 Structured Diagnosis & Offline Deterministic Execution
- **Assumption**: Structured root-cause diagnosis executes purely offline via `DeterministicDiagnosisProvider` by default, with 0 external API dependencies. An optional `LLMDiagnosisProvider` is supported and automatically falls back to deterministic offline rules if unconfigured, timed out, or malformed.
- **Implication**: Evaluators can clone the repository and run all verification scripts (`python -m pytest -v` and `python scripts/demo.py`) with zero setup overhead and zero required API keys.

## 2. Economic & Financial Assumptions

### 2.1 Customer Churn Friction Penalty Proxy
- **Assumption**: The evaluation metric models customer churn using a configurable economic proxy:
  $$\text{Default Churn Penalty} = \text{₹2,500 (250,000 paise per churned customer)}$$
- **Implication**: This penalty represents an approximation of lost customer Lifetime Value (LTV) caused by aggressive messaging or payment link spam. Live deployments can customize this parameter to match their merchant cohort's specific customer LTV.

### 2.2 Negative Uplift & Action Cost Approximations
- **Assumption**: Incremental recovery uplift is computed as $\Delta P = P(a) - P(\text{no\_action})$ without artificial floor clipping, allowing negative uplift ($\Delta P < 0$) and negative expected net value. Direct intervention execution costs are parameterized as:
  - `NO_ACTION`: ₹0.00 (0 paise)
  - `RETRY_NOW`: ₹0.20 (20 paise gateway surcharge estimate)
  - `RETRY_LATER`: ₹0.20 (20 paise gateway surcharge estimate)
  - `PAYMENT_LINK`: ₹1.00 (100 paise SMS/WhatsApp + hosted page fee)
  - `REMINDER`: ₹0.50 (50 paise notification fee)
- **Implication**: Action costs and negative uplift incentivize the policy to abstain when intervention does not beat the natural recovery baseline or when costs exceed expected returns.

## 3. Behavioral & Policy Assumptions

### 3.1 Customer Behavioral Archetypes
- **Assumption**: Customers belong to one of four synthetic archetypes (`HIGHLY_RESPONSIVE`, `NATURAL_RECOVERER`, `CONTACT_FATIGUED`, `NON_RESPONSIVE`) with fixed response distributions and contact sensitivity penalties.
- **Implication**: In production, real-world customer behavior is continuous, multi-dimensional, and non-stationary, requiring live bandit learning or uplift modeling.

### 3.2 Deterministic Proxy Policy & Confidence Gates
- **Assumption**: The baseline policy (`DeterministicRecoveryPolicy`) uses structured diagnosis taxonomy labels (`DiagnosisLabel`) and observable context, applying confidence gates (`confidence_threshold = 0.50`) and expected-value ranking.
- **Implication**: The deterministic policy provides an interpretable, transparent benchmark demonstrating the value of structured diagnosis, expected-value optimization, physical constraint filtering, and active abstention.

### 3.3 Recovery Governor & Merchant Policy Contract
- **Assumption**: Autonomous actions pass through `RecoveryGovernor` evaluating versioned `MerchantPolicy` rules (automation modes, retry caps, 24h contact limits, amount thresholds, cooldowns, and human review routing).
- **Implication**: The Governor acts as the deterministic execution authority, ensuring zero unauthorized dunning actions execute without passing merchant policy checks.

---

## 4. Systems & Persistence Assumptions

### 4.1 In-Memory Reference Storage
- **Assumption**: For standalone testing and submission evaluation, `InMemoryEventStore`, `InMemoryIdempotencyTracker`, `InMemoryScheduledStore`, and `DecisionLogStore` operate in process memory.
- **Implication**: Production deployments require distributed, persistent infrastructure (e.g. PostgreSQL event streams, Redis distributed locks, temporal queues, and S3 compliance logs).

### 4.2 Discrete Timing Windows & State Versioning
- **Assumption**: Action timing is modeled across discrete candidate windows (`IMMEDIATE`, `PLUS_2H`, `PLUS_6H`, `PLUS_12H`, `PLUS_24H`) with expected net recovery estimates parameterized per mechanism-window pair. Scheduled actions record the aggregate state version at creation (`expected_state_version`) and revalidate against current aggregate state prior to execution.
- **Implication**: Discrete timing provides deterministic, verifiable scheduling benchmarks. Production deployments can extend this with continuous-time survival analysis or time-to-event uplift models while preserving the Governor revalidation and stale invalidation lifecycle.
